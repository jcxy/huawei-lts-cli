# ADR-0001: 公开 skill 与本地 profile 双轨分离

- **状态**：已被 [ADR-0004](0004-retire-local-profile.md) 取代（Superseded）
- **日期**：2026-10-24

## 背景

`SKILL.md` 与 `references/cheatsheet.md` 曾硬编码一整套具体环境的事实：日志组名与 ID、日志流 ID、应用名清单（32 个）、以及该环境的索引字段表。这些内容对作者所在环境准确，但：

1. 对其他任何 LTS 用户都是**错误信息**——字段名不存在、日志组不存在，AI 会据此构造查不到的查询；
2. 会随环境变化而过期，且没有任何机制提醒它过期；
3. 部分内容属于内部信息，不应出现在公开仓库。

同时，删掉全部环境信息会让日常使用效率倒退——AI 失去「订单服务 → 某个 appName」这类业务词到日志值的映射能力。

## 决策

拆成两层，由文件边界强制隔离：

- **公开 skill** 只描述「如何发现」：`groups` → `streams` → `fields` → `query`。不含任何具体值。
- **`~/.lts-cli/profile.md`** 承载 API 拿不到的业务词义：应用名映射、命名约定、团队黑话。由 AI 读取，**不进入仓库**。
- **`~/.lts-cli/config.json`** 承载 CLI 行为配置：凭证、`traceField`、默认 group/stream。由 CLI 读取，**AI 不得读取**。

profile 只装 API 拿不到的东西。字段表、日志组/流清单一律不写进去——那些靠 `fields` / `groups` / `streams` 实时获取。往 profile 里抄一份，就是制造第二个会过期的真相来源，而这正是本次改造要解决的问题。

profile 缺失是**正常状态**。skill 必须写成「存在则读，不存在则走通用发现流程」，不得报错。

## 取舍

- 代价：多一个文件、`init` 多一步生成、用户多一次「填业务名」的配置成本。
- 收益：公开 skill 对所有 LTS 用户成立；凭证永远不会进入 AI 上下文；内部信息有了正确的存放位置而不是被删除。

## 被否方案

- **全部保留**：继续泄漏内部信息，且对其他用户是错的。
- **全部删除**：日常效率倒退，AI 失去业务词映射能力。
- **放进 `config.json`**：凭证与业务事实混在一处，AI 一旦读取就整份 AK/SK 进上下文。这是本次明确要消除的风险，不能重新引入。

## 适用条件与失效条件

当前成立。若 LTS 未来提供服务端可存的业务元数据（如日志流标签、命名空间），profile 可以退休，业务词义改为随日志流存储。
